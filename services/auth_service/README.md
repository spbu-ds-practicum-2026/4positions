# TimeBook Auth Service

Самостоятельный сервис регистрации и входа на FastAPI + PostgreSQL. Не требует Gateway, TimeBook или папки common. HTTP-контракт прежний: `POST /auth/register`, `POST /auth/login`, `GET /health`. JWT RS256, Argon2id, срок JWT по умолчанию 1800 секунд. `/health` проверяет живость сервиса, не соединение с БД.

## Windows (CMD), Python 3.12

Скопируйте папку `auth_service` в корень общего проекта. Далее команды выполняются **внутри** `auth_service`.

```cmd
py -3.12 -m venv .venv
.venv\Scripts\activate.bat
python -m pip install -r requirements.txt
copy .env.example .env
```

Откройте `.env` и подставьте пароль PostgreSQL пользователя `auth_user` вместо `YOUR_PASSWORD`. Если пароль содержит спецсимволы, URL-кодируйте пароль. Предполагается, что локальная база `auth_db` уже создана, её владелец `auth_user`, порт 5432. Если база ещё не создана, в SQL Shell от имени postgres выполните `CREATE ROLE auth_user LOGIN;`, затем `\password auth_user` и `CREATE DATABASE auth_db OWNER auth_user;`.

Если переносите старую конфигурацию, скопируйте только нужные параметры из прежнего `.env` в новый. Ключи из прежней папки `keys` можно перенести внутрь `auth_service/keys`, чтобы уже выпущенные токены продолжили работать. Не генерируйте новые ключи поверх старых. Относительные пути ключей в `.env` отсчитываются от папки `auth_service`; переменные окружения, уже установленные в терминале, имеют приоритет над `.env`.

```cmd
python generate_keys.py
python main.py
```

Генератор запускается один раз, если ключей ещё нет. `main.py` при запуске сам создаёт таблицу через `database.py`, если её ещё нет (не удаляет и не изменяет существующие записи). Если БД недоступна или нет прав на создание таблицы, запуск завершится ошибкой. Сама база и роль PostgreSQL должны быть созданы заранее. Сервер остаётся работать на http://127.0.0.1:8002. В другом терминале CMD:

```cmd
cd путь\к\проекту\auth_service
.venv\Scripts\activate.bat
python test.py
```

Пункт 8 — автоматические HTTP-проверки. Для запуска без меню:

```cmd
python test.py --auto
```

Клиент обращается к работающему сервису, проверяет JWT по публичному ключу и создаёт два тестовых логина за успешный прогон; они остаются в БД. Выход из аккаунта лишь удаляет токен в клиенте. Можно указать `--url` и `--public-key`; по умолчанию берётся локальный публичный ключ или `JWT_PUBLIC_KEY_FILE` из конфигурации.

## Автоматические тесты pytest

Запуск из папки `auth_service` (сервер запускать не надо):

```cmd
python -m pytest -v
```

Тесты проверяют регистрацию, вход, уникальность, хеширование, валидацию, обработку отказа БД и JWT. По умолчанию используется тестовое хранилище в памяти. Тест настоящей БД пропускается, пока не задана переменная `TEST_AUTH_DATABASE_URL`. Для него рекомендуется отдельная тестовая БД (например, `CREATE DATABASE auth_test_db OWNER auth_user;` от postgres). В CMD:

```cmd
set "TEST_AUTH_DATABASE_URL=postgresql://auth_user:YOUR_PASSWORD@127.0.0.1:5432/auth_test_db"
python -m pytest -v test_auth.py -k postgres
```

Этот тест создаёт таблицу при необходимости, проверяет два конкурентных запроса, удаляет только свой случайный тестовый логин. Не запускайте его на production БД. Не храните реальные пароли или JWT в репозитории.

Из корня общего проекта можно запустить `python -m auth_service.main`, `python -m auth_service.test` и `python -m pytest auth_service/test_auth.py`. Для обычного использования удобнее запускать команды внутри `auth_service`.

## Структура

- `main.py` — HTTP API, загрузка `.env`, инициализация таблицы и запуск сервера.
- `database.py` — PostgreSQL, в том числе SQL создания таблицы.
- `auth.py` — модели и функции JWT (раньше common/auth.py).
- `.env.example` — шаблон конфигурации.
- `generate_keys.py` — локальная генерация RSA.
- `test.py` — консольный клиент и HTTP-демонстрация.
- `test_auth.py` — pytest-тесты.
- `requirements.txt` — все зависимости, включая pytest.

`.env`, `keys/`, `.venv/` исключены из Git. Приватный ключ не передавать другим компонентам. Вне локальной разработки необходимы защищённый транспорт, ограничение попыток входа и управление ключами; эти механизмы пока не добавлены. При интеграции Gateway будет проверять JWT публичным ключом и передавать проверенный идентификатор пользователя.
